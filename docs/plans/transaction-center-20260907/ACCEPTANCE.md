# 交易中心可验证验收与发布门禁

状态：验收方案，尚未执行业务测试、压测、容灾或渠道认证。每项必须提交构建 SHA、环境、数据集／种子版本、命令、原始结果及责任人；不能仅附截图写“通过”。

## 1. 功能与一致性验收矩阵

| 编号 | 操作／故障注入 | 必须观测的通过条件 |
|---|---|---|
| TC-01 | 同一租户／登录主体100并发注册 | 仅1会员、1有效身份映射、1业务注册事件；全部成功响应指向同会员 |
| TC-02 | 不同租户使用相同外部 subject；伪造会员 ID | 身份相互隔离；未授权读写0条；审计不泄露其他租户对象存在性 |
| TC-03 | 注册时 DB 提交后响应丢失再重试 | 无重复会员；Outbox 恢复后最终送达 |
| TC-04 | 商品发布后改价格，使用有效旧报价下单 | 按报价锁价；过期报价拒绝；已下架 SKU 拒绝新下单；历史订单快照不变 |
| TC-05 | 修改客户端金额、币种、SKU 数量或归因令牌 | 服务端拒绝篡改，金额越界／负数／无权令牌均不能创建订单 |
| TC-06 | 库存100，1000并发下单各1件 | 成功预占≤100，库存不负；余额等于流水聚合；其余明确库存不足或限流 |
| TC-07 | 多 SKU 订单最后一个 SKU 库存不足 | 订单不成功，前面 SKU 无残留预占；事务回滚无孤儿流水 |
| TC-08 | 同键重复下单100次／同键不同请求体 | 前者只1订单1组预占；后者409；响应丢失可找回原订单 |
| TC-09 | 预占与取消、确认同时执行，重复各100次 | 预占只能到一个合法终态；不能既卖出又释放；总量守恒 |
| TC-10 | 渠道创建已受理但本地超时 | UNKNOWN保留；相同请求号查询／重试；不创建第二笔不受控扣款 |
| TC-11 | UNKNOWN期间切换支付渠道 | 返回未决冲突；旧渠道可靠关闭后才允许新尝试 |
| TC-12 | 重复／乱序支付回调，各重放100次 | 仅1正常收款账本、1订单支付转换、1库存确认、1履约；成功不回退失败 |
| TC-13 | 错签、错商户、错币种、错金额回调 | 错签不确认资金；已验签真实异常资金保留待处理事实，订单不正常履约 |
| TC-14 | 两笔不同真实交易号都对同订单收款成功 | 两笔资金事实都保留，仅1次履约；多付进入唯一补偿退款流程 |
| TC-15 | 订单过期时渠道支付成功与关单竞争 | 成功支付则确认库存；可靠关闭才释放；每种交错无超卖／丢款 |
| TC-16 | 在本地关单后恢复暂停的支付工作者 | 工作尝试受 close fence约束；对可能已在途调用验证渠道关闭屏障，不仅测试本地状态 |
| TC-17 | 已取消释放库存后注入渠道矛盾成功 | 不复活订单、不重复占已售库存；入账并触发原路补偿与报警 |
| TC-18 | 回调到达时数据库断开／提交后断响应 | 未持久接收不应答成功；提交后重试靠事件键去重，最终收款处理一次 |
| TC-19 | 同会员两订单并发支付，之后补早时间戳回调 | 仅一个 FIRST_CONFIRMED_PAID_ORDER_V1；迟到早时间戳不篡改首单 |
| TC-20 | 首单全额退款后再购买／查询新客 | everPaid保持真、原首单标记不换；营销按净支付策略撤销资格而不是恢复新客 |
| TC-21 | 实收10000，20并发各申请退款1000 | 接受退款总额≤10000；成功＋预占≤实收；重复请求不多占额度 |
| TC-22 | 退款已被渠道受理后超时，重复通知成功 | 额度保持预占直至查明；仅1退款账本；相同退款号重试不重复退款 |
| TC-23 | 部分退款商品／运费／税分配并发执行 | 明细及订单累计退款不超冻结可退额；分摊无丢分／多分 |
| TC-24 | 退款成功但未收到退货；重复验收入库 | 前者库存不增加；后者仅1次入库，累计退货不超过原履约数量 |
| TC-25 | 伪造审批结果、旧版本重放、自审自批 | 全部拒绝；合法审批仅触发1次执行；渠道已执行退款不得人工改成拒绝 |
| TC-26 | Outbox 发布确认后进程宕机再恢复 | 允许消息重复，但不漏业务事实；消费者业务效果至多一次 |
| TC-27 | 退款事件先于支付／完成事件到达营销 | 消费者按版本查询最新证据，不恢复已取消奖励；最终与交易事实一致 |
| TC-28 | 渠道账单多款、少款、跨日退款、手续费、更正 | 每种生成正确差异或核平；修复命令幂等，保留审批及账单证据 |
| TC-29 | 会员冻结／匿名化后退款回调到达 | 合法资金事实仍能处理，展示遵循隐私策略；不删除审计证据 |
| TC-30 | 零元订单下单／完成 | 不调用真实支付接口，不伪造渠道交易号，默认不占消费首单 |
| TC-31 | 重放超过幂等响应快照保留期的支付请求 | 渠道请求号与业务唯一约束仍防重复支付，不因技术表清理失效 |
| TC-32 | 租约到期后旧Worker恢复写结果 | fencing/CAS拒绝陈旧状态更新；外部重复调用仍沿用同一幂等号 |

## 2. 自动化不变量和测试层次

每次回归断言：

- 每个库存余额行均非负且 available+reserved+sold=stock_total；从库存初始种子＋流水重算与余额一致。
- 每个 receipt 的 refunded_amount+refund_reserved_amount≤amount；账本与支付／退款确认事实逐笔对应，无孤儿或重复业务键。
- 每个订单应付等于明细应付＋运费＋税；正常订单实收与应付同币种同金额；多付不被计入正常消费额。
- 同一会员只有一个首单事实，退款不能把 everPaid 清零；会员事实、订单状态和相关 Outbox 在同事务可见。
- inbox唯一键与副作用一并提交；对任何合法事件序列重复100次，最终业务结果不变。

测试层次：纯领域单元／属性测试（随机状态序列、金额边界）；真实 MySQL 集成测试（不能用 H2 模拟行锁）；本地模拟渠道的网络故障与幂等测试；真实渠道沙箱合同测试；跨项目 E2E；最后独立压测与容灾。模拟渠道必须使用专用测试配置，生产启动检查拒绝它。

建议实施文件：`InventoryConservationPropertyTest`、`PaymentCloseRaceIT`、`ConcurrentRefundIT`、`FirstPaidOrderRaceIT`、`TenantIsolationIT`、`OutboxRecoveryIT`、`PaymentChannelContractTest`、`SchemaCommentGateTest`、`ModuleBoundaryTest`。这些名称为计划，不代表测试已创建。

## 3. 性能容量验收方法

使用[总纲容量表](FINAL_PLAN.md)的单 cell 目标；硬件资源和数据库／中间件版本冻结后测试。数据基线：100万会员、10万SKU、1000万历史订单、3000万订单明细、相应支付和账本；使用数据库种子／生成脚本，非前端内存数组。数据分布包含大租户、冷租户、热点 SKU 和长历史会员。

1. 各端点单项爬坡，再按容量表目标混合运行30分钟，记录开放模型实际发出RPS而非仅客户端线程数；不得用排队客户端隐藏过载。
2. 各目标值为同 cell 联合预算，混合负载不达标即需调整设计／资源并重测，不把单接口最高值相加宣传。
3. 10%步骤爬坡至拐点，记录吞吐、P50/P95/P99、内部错误率、队列、锁等待、磁盘和数据库连接；正常容量内部失败率<0.1%，合法库存不足／风险拒绝另计但完整披露。
4. 两倍突发持续5分钟：允许明确429/503，禁止超卖、重复扣款、进程OOM、无界队列；回落后5分钟内恢复基线、10分钟内清空突发可处理积压。
5. 热点：80%订单请求单SKU单仓，固定有限库存。允许热点保护拒绝；发布热点实际可接受吞吐，不强求其等于均匀分布500RPS。开启库存桶须独立复测桶间守恒与迁移。
6. 冷缓存、缓存完全不可用分别测试；降级后的安全容量须明确公布，不能继续承诺热缓存吞吐。
7. 50%混合峰值运行8小时：无持续内存增长、连接泄漏、未知支付年龄无界增长。第三方支付采用授权压测沙箱或模拟器，真实渠道吞吐单独凭渠道限额和沙箱结果确认，不能压真实商户。

报告附件：负载脚本、数据生成SHA、原始直方图、Prometheus查询、DB慢SQL及EXPLAIN、锁冲突分布、GC/CPU/IO、成功／限流／业务拒绝／错误四类计数，端到端资金与库存不变量结果。

## 4. 高可用与恢复验收

| 故障 | 验证步骤 | 通过条件 |
|---|---|---|
| API／回调Pod宕机 | 目标负载中随机杀实例 | 无已确认事实丢失、重复受理幂等；剩余容量按冗余预算处理 |
| 单AZ中断 | 隔离AZ网络和该AZ实例 | 目标RTO≤5min；按实际DB策略验证已确认交易RPO；不出现双主写 |
| 数据库切主 | 在提交、回调应答、Outbox确认边界故障 | 客户端可能未知但可找回结果；旧主隔离，未知事务以业务键核实 |
| 消息平台不可用30min | 禁止生产者投递再恢复 | 事实和Outbox不丢；恢复后按限额排空；磁盘阈值触发保护而非写满 |
| Redis不可用 | 关闭缓存连接 | 核心正确性保持，限量回源，数据库未被击穿 |
| 支付渠道超时／抖动 | 注入超时、慢响应、重复通知 | UNKNOWN受控、查单恢复、不盲切渠道；告警覆盖最长未决年龄 |
| 备份恢复 | 隔离环境执行恢复并校验业务数据 | 目标异地RPO≤5min/RTO≤30min有时间戳证据；禁用真实外部副作用 |
| 密钥轮换 | 新旧渠道证书过渡、吊销旧证书 | 过渡期合法通知可验，失效证书不能继续授权，审计可追踪 |

RPO=0只有实际数据库持久性和切换策略支撑且演练通过才可写入 SLA。基础设施不能满足时在评审中下调承诺或升级方案，禁止用应用重试掩盖数据丢失。

## 5. 安全、注释及工程门禁

- SAST／依赖／镜像扫描：无未豁免阻断级漏洞；SQL绑定参数、SSRF返回地址白名单、鉴权绕过、对象越权和重放用例通过。
- 数据库注释：全部新表和字段100%具有准确中文注释，包括新增字段、关联表、种子表、Outbox/Inbox；迁移后自动查询 information_schema 产出报告，空注释为零。
- 后端注释：新增类、公共方法 Javadoc 覆盖100%；复杂状态、锁顺序、资金／库存不变量和异常分支必须说明原因。人工核对注释与代码一致，禁止使用重复模板敷衍门禁。
- 核心领域分支覆盖率建议≥90%，改动行覆盖≥80%，但 TC-01～32业务测试不得由覆盖率替代；测试禁止时间脆弱的固定 sleep，应使用可控制时钟和最终条件等待。
- OpenAPI／AsyncAPI schema校验、破坏性变更检查、提供者／消费者合同测试、ArchUnit边界检查全部通过；禁止跨模块Mapper和前端硬编码Mock业务数据。
- 本地公共中间件优先复用dev-infra；生产凭据通过Secret/KMS，不入Git；测试种子仅写测试DB，有环境拦截。

## 6. 发布签署与交接

发布必须齐备：业务口径签署、渠道合同与沙箱证据、数据字典＋完整迁移、API／事件schema、TC用例报告、容量报告、容灾报告、监控告警、值班与事故联系人、对账日报与差异处置Runbook、回滚演练、Cursor前端接口验收。

阻断项：真实渠道缺失、关单终态不可证明、超卖／重复退款／资金事实丢失、租户越权、建表缺注释、关键故障不可恢复、对账差异无人负责。不能以“后续优化”放过这些问题。

当前可继续的实施前置：确认首期渠道及商户、是否实物商品、首单口径与奖励观察期、生产容量预算、组织负责人。现有设计已给出默认边界，可据此拆开发任务；业务代码开发须另获实施批准。
